@topic ansible | Ansible | #EE0000 | gear | Agentless automation: inventory, playbooks, roles, templates, vault and real projects.

= ans-what-is | What is Ansible? Start here | 1 | gear | Eight plain steps: the problem, the agentless idea, inventory, playbook, modules, idempotence and where Ansible fits.
> The problem: the same job on many servers | users
text: Imagine installing a web server on ten machines. Typing the same commands ten times is slow, and the machines slowly drift apart because a step was missed on number seven. You need a way to describe the result you want once and apply it everywhere.
> Ansible in one sentence | gear
text: Ansible is an automation tool. You write down the state you want (a package installed, a file in place, a service running) and Ansible makes each machine match it. It is free, open source and uses plain text files that you can keep in Git.
> Agentless: nothing to install on the servers | network
text: There is no agent or background program on the managed servers. Your own computer, the control node, connects over SSH, runs small tasks and disconnects. The servers only need SSH access and Python.
viz: Control node>web1:SSH, run task ; Control node>web2:SSH, run task ; web1>Control node:result ; web2>Control node:result
> Inventory: which machines | table
text: The inventory is a list of your servers, organised into groups such as web and db. It answers the question "where?".
cmd: cat inventory.ini
out: [web]\nweb1.example.com\nweb2.example.com\n\n[db]\ndb1.example.com
> Playbook: what to do | doc
text: A playbook is a YAML file that lists tasks for a group of hosts. It answers the question "what?". Read it top to bottom like a checklist.
cmd: cat site.yml
out: - name: Install and start Apache\n  hosts: web\n  become: true\n  tasks:\n    - name: Install the package\n      ansible.builtin.package:\n        name: apache2\n        state: present
> Modules: the building blocks | package
text: Each task calls a module, a small tested program such as package, copy, template, service or user. Modules are written to be safe to repeat. You rarely write shell commands yourself.
cmd: ansible-doc -l | head -n 5
cmd: ansible-doc ansible.builtin.copy | head -n 20
> Idempotent: safe to run again | retry
text: Idempotent means running it twice gives the same result as running it once. Ansible checks first and only changes what is different. The summary shows ok for things already correct and changed for things it fixed.
out: PLAY RECAP *********************************************\nweb1.example.com : ok=3 changed=0 unreachable=0 failed=0
note: The first run usually shows changed. A second run showing changed=0 is the proof that the system matches your description.
> Where Ansible fits | layers
text: Terraform creates infrastructure (servers, networks, load balancers). Ansible configures what runs on it (packages, files, users, services). Docker packages an application with its dependencies. Teams often use the three together: Terraform builds the server, Ansible prepares it and Docker runs the app.

= ans-architecture | Ansible architecture: control node to managed nodes | 1 | network | Follow one command through the control node, inventory, modules, SSH and the managed nodes.
> Control node | laptop
text: The control node is the machine where Ansible is installed and where you run commands. It can be a laptop or a small jump server. It holds your inventory, playbooks and roles. Managed nodes never need Ansible.
> Managed nodes | server
text: Managed nodes are the servers and devices you configure. They need SSH and a Python interpreter for most modules. Windows hosts use WinRM or SSH instead.
> Inventory selects the targets | table
text: When you run a command, Ansible reads the inventory, expands groups and patterns into a list of hosts and loads variables for each.
cmd: ansible-inventory -i inventory.ini --graph
out: @all:\n  |--@ungrouped:\n  |--@web:\n  |  |--web1.example.com\n  |  |--web2.example.com
> One task, step by step | pipeline
text: For each task and each host Ansible connects, copies a small module script to a temporary folder, runs it with the arguments, collects the JSON result and removes the temporary files. Hosts run in parallel, 5 at a time by default (forks).
viz: Control node>web1:1 connect (SSH) ; Control node>web1:2 copy module to temp dir ; Control node>web1:3 run module ; web1>Control node:4 JSON result ; Control node>web1:5 remove temp files
cmd: ansible-config dump --only-changed
cmd: ansible-config dump | grep -i forks
> Playbooks, roles and collections | package
text: A playbook is a list of plays, each mapping a host group to tasks. Roles package related tasks for reuse. Collections distribute modules, roles and plugins, for example ansible.posix or community.docker.
cmd: ansible-galaxy collection list
> Facts and results | search
text: At the start of each play Ansible gathers facts about each host (OS, IP addresses, memory). It reports ok, changed, failed or unreachable per host, then a recap.
cmd: ansible web1.example.com -i inventory.ini -m ansible.builtin.setup -a "filter=ansible_distribution*"
out: web1.example.com | SUCCESS => {\n    "ansible_facts": {\n        "ansible_distribution": "Ubuntu",\n        "ansible_distribution_release": "noble"\n    },\n    "changed": false\n}

= ans-install-first-ping | Install Ansible and run your first ping | 1 | download | Install with pipx, create an inventory, check SSH access and run the ping module.
> Check Python | code
text: Ansible is a Python program. Check the version on the control node. Use the Python that your OS ships or one you installed yourself.
cmd: python3 --version
> Install Ansible | download
text: The Ansible documentation recommends pipx, which installs a command-line tool in its own isolated environment. --include-deps exposes the ansible commands. If you prefer, python3 -m pip install --user ansible also works.
cmd: pipx install --include-deps ansible
cmd: ansible --version
out: ansible [core 2.18.x]\n  config file = None\n  python version = 3.12.x
note: The package named ansible includes many collections. The package ansible-core is the minimal engine. Version numbers move quickly, so yours will differ.
> Create a project folder and inventory | folder
text: Keep everything for one automation project in one folder. The inventory lists your servers. Replace the names with your own servers.
cmd: mkdir -p ~/ansible-lab && cd ~/ansible-lab
cmd: printf '[web]\nweb1.example.com\nweb2.example.com\n' > inventory.ini
cmd: cat inventory.ini
> Set defaults in ansible.cfg | sliders
text: A local ansible.cfg saves repeating options on every command. Here it sets the inventory file, the login user and the SSH settings.
cmd: cat > ansible.cfg <<'EOF'\n[defaults]\ninventory = inventory.ini\nremote_user = ubuntu\nhost_key_checking = True\nEOF
> Check that you can log in by hand | key
text: Ansible uses the same SSH access you use. If this fails, Ansible will fail too. Fix SSH first.
cmd: ssh ubuntu@web1.example.com hostname
> Run the ping module | bolt
text: This is not an ICMP network ping. The ping module logs in over SSH, finds Python and returns "pong". SUCCESS means SSH, login and Python are all working.
cmd: ansible all -m ansible.builtin.ping
out: web1.example.com | SUCCESS => {\n    "changed": false,\n    "ping": "pong"\n}\nweb2.example.com | UNREACHABLE! => {\n    "msg": "Failed to connect to the host via ssh: ...Connection timed out"\n}
note: UNREACHABLE means a connection problem (name, network, firewall, key or user). FAILED means it connected but the task failed.
> Read errors and use -v | bug
text: Add -v for more detail, up to -vvvv for connection debugging. Most first-day problems are SSH keys, the wrong user, a missing Python or a host key prompt.
cmd: ansible web1.example.com -m ansible.builtin.ping -vvv
cmd: ansible all -m ansible.builtin.ping -u ubuntu --private-key ~/.ssh/id_ed25519

= ans-inventory-ini | Inventory in INI format | 1 | table | From a flat list of hosts to groups, variables and groups of groups, then inspect and target them.
> A flat list of hosts | table
text: The simplest inventory is one host per line. Hosts outside any group belong to the built-in groups all and ungrouped.
cmd: cat > inventory.ini <<'EOF'\nweb1.example.com\nweb2.example.com\ndb1.example.com\nEOF
> Put hosts into groups | layers
text: A group name in square brackets starts a section. Playbooks target groups, so grouping is how you say "all web servers".
cmd: cat > inventory.ini <<'EOF'\n[web]\nweb1.example.com\nweb2.example.com\n\n[db]\ndb1.example.com\nEOF
> Variables on hosts and groups | sliders
text: ansible_host sets the real address when the name is not resolvable. [group:vars] sets variables for every host in the group.
cmd: cat > inventory.ini <<'EOF'\n[web]\nweb1 ansible_host=10.0.1.11\nweb2 ansible_host=10.0.1.12\n\n[db]\ndb1 ansible_host=10.0.2.21\n\n[web:vars]\nhttp_port=80\n\n[all:vars]\nansible_user=ubuntu\nEOF
> Groups of groups | branch
text: [parent:children] lists groups instead of hosts. Targeting prod now covers both web and db.
cmd: printf '\n[prod:children]\nweb\ndb\n' >> inventory.ini
cmd: ansible-inventory -i inventory.ini --graph
out: @all:\n  |--@ungrouped:\n  |--@prod:\n  |  |--@web:\n  |  |  |--web1\n  |  |  |--web2\n  |  |--@db:\n  |  |  |--db1
> Inspect what Ansible sees | search
text: --host prints all variables for one host, merged from every level. --list prints everything as JSON.
cmd: ansible-inventory -i inventory.ini --host web1
cmd: ansible-inventory -i inventory.ini --list | head -n 20
> Target with patterns | filter
text: Patterns pick hosts. A colon means OR, :& means AND, :! means NOT. --list-hosts shows the result without running anything.
cmd: ansible 'web' -i inventory.ini --list-hosts
cmd: ansible 'prod:!db' -i inventory.ini --list-hosts
cmd: ansible 'web:&prod' -i inventory.ini --list-hosts
out:   hosts (2):\n    web1\n    web2

= ans-inventory-yaml | Inventory in YAML, group_vars and host_vars | 2 | folder | The same inventory as YAML, then move variables into group_vars and host_vars files.
> The YAML inventory shape | doc
text: Everything sits under all. Groups live under children, each with hosts and optional vars. YAML is indentation-sensitive: use spaces, never tabs.
cmd: cat > inventory.yml <<'EOF'\nall:\n  children:\n    web:\n      hosts:\n        web1.example.com:\n        web2.example.com:\n      vars:\n        http_port: 80\n    db:\n      hosts:\n        db1.example.com:\n          ansible_host: 10.0.20.5\n  vars:\n    ansible_user: ubuntu\nEOF
> Check it parses | check
text: Let Ansible read it back. A syntax mistake shows up as a clear error, usually a wrong indent.
cmd: ansible-inventory -i inventory.yml --graph
cmd: ansible-inventory -i inventory.yml --host db1.example.com
> Move variables to group_vars | folder
text: Files named after a group inside group_vars are loaded automatically. This keeps the inventory short and the variables easy to find.
cmd: mkdir -p group_vars host_vars
cmd: printf 'http_port: 8080\nserver_admin: ops@example.com\n' > group_vars/web.yml
cmd: ansible-inventory -i inventory.yml --host web1.example.com
> Per-host overrides | edit
text: host_vars/<host>.yml sets values for one machine. It beats group_vars for the same variable, which is how you make one exception.
cmd: printf 'http_port: 9090\n' > host_vars/web2.example.com.yml
cmd: ansible-inventory -i inventory.yml --host web2.example.com | grep http_port
out:     "http_port": 9090,
> Precedence in one sentence | up
text: More specific wins: group_vars/all is overridden by a specific group, which is overridden by host_vars, then playbook variables, and finally -e on the command line beats everything. When a value surprises you, check with ansible-inventory --host.

= ans-adhoc | Ad-hoc commands for quick jobs | 1 | terminal | One-line commands for checks and small changes, and when to switch to a playbook.
> The shape of an ad-hoc command | terminal
text: ansible <pattern> -m <module> -a "<arguments>". It runs one module on the chosen hosts, right now, without a playbook.
viz: You>Control node:ansible web -m ping ; Control node>web1:run module ; Control node>web2:run module ; web1>You:pong ; web2>You:pong
cmd: ansible web -i inventory.ini -m ansible.builtin.ping
> Run a command | play
text: The command module runs a program without a shell. The shell module uses a shell, so pipes and redirects work, at the cost of safety. Prefer command.
cmd: ansible web -i inventory.ini -m ansible.builtin.command -a "uptime"
cmd: ansible web -i inventory.ini -m ansible.builtin.shell -a "df -h / | tail -n 1"
> Gather facts | search
text: The setup module returns facts. Use filter to keep the output short.
cmd: ansible web -i inventory.ini -m ansible.builtin.setup -a "filter=ansible_memtotal_mb"
> Copy a file | upload
text: The copy module sends a local file to the servers and sets the owner and mode. It only reports changed if the content differs.
cmd: echo "managed by ansible" > motd.txt
cmd: ansible web -i inventory.ini -b -m ansible.builtin.copy -a "src=motd.txt dest=/etc/motd mode=0644"
> Become root and manage a service | key
text: -b (become) uses sudo. The package and service modules work on any distribution, so the same command works on Ubuntu and RHEL.
cmd: ansible web -i inventory.ini -b -m ansible.builtin.package -a "name=htop state=present"
cmd: ansible web -i inventory.ini -b -m ansible.builtin.service -a "name=cron state=restarted"
> When to write a playbook instead | doc
text: Ad-hoc is for checks and one-off jobs. As soon as you want to repeat it, review it, share it or run several steps in order, put it in a playbook and commit it to Git.

= ans-yaml-basics | YAML basics for Ansible | 1 | doc | The handful of YAML rules that cause most beginner errors: indentation, lists, dictionaries, quoting and booleans.
> Key and value | edit
text: A dictionary is a set of key: value pairs. There must be a space after the colon.
cmd: printf 'name: web1\nport: 80\n' > demo.yml
cmd: cat demo.yml
> Lists | menu
text: A list item starts with a dash and a space. Items line up at the same indentation. Playbooks and task lists are lists of dictionaries.
cmd: printf 'packages:\n  - nginx\n  - git\n  - curl\n' > demo.yml
cmd: python3 -c "import yaml,sys;print(yaml.safe_load(open('demo.yml')))"
out: {'packages': ['nginx', 'git', 'curl']}
note: This check needs PyYAML (pip install pyyaml). yamllint is a better tool for style checks.
> Indentation | layers
text: Use two spaces per level and never tabs. Children must be indented more than their parent. Mixed indentation is the most common cause of "mapping values are not allowed here" errors.
> Quote values that start with a Jinja2 expression | warn
text: A value that begins with {{ must be quoted, otherwise YAML reads it as a dictionary. This is the most common Ansible-specific mistake.
cmd: printf 'good: "{{ http_port }}"\nbad: {{ http_port }}\n' > demo.yml
cmd: python3 -c "import yaml;yaml.safe_load(open('demo.yml'))"
out: yaml.scanner.ScannerError or ConstructorError: found unhashable key
note: The second line is deliberately wrong to show the error.
> Booleans and strings | check
text: In YAML 1.1 words such as yes, no, on and off can become booleans. Use true and false in new files. Quote anything that must stay a string, such as a version 3.10 or a file mode "0644".
cmd: printf 'enabled: true\nversion: "3.10"\nmode: "0644"\n' > demo.yml
> Multi-line text | doc
text: A | keeps line breaks (good for scripts and file content). A > folds lines into one (good for long sentences).
cmd: printf 'motd: |\n  Welcome to the server.\n  Managed by Ansible.\n' > demo.yml
cmd: python3 -c "import yaml;print(repr(yaml.safe_load(open('demo.yml'))['motd']))"
out: 'Welcome to the server.\nManaged by Ansible.\n'
> Validate before you run | check
text: yamllint catches style and syntax problems. ansible-playbook --syntax-check understands Ansible structure. Use both.
cmd: yamllint site.yml
cmd: ansible-playbook site.yml --syntax-check

= ans-first-playbook | Your first playbook | 1 | doc | Write a playbook that installs a package and starts a service, then check, preview, run and rerun it.
> The anatomy of a playbook | doc
text: A playbook is a list of plays. Each play has a name, the hosts it targets, whether to become root and a list of tasks. Each task has a name and calls one module with arguments.
> Write site.yml | edit
text: Two tasks: install Apache and make sure it is running and enabled at boot. The package name is apache2 on Debian and Ubuntu (it is httpd on RHEL).
cmd: cat > site.yml <<'EOF'\n- name: Install and start Apache\n  hosts: web\n  become: true\n  tasks:\n    - name: Install Apache\n      ansible.builtin.package:\n        name: apache2\n        state: present\n    - name: Start and enable Apache\n      ansible.builtin.service:\n        name: apache2\n        state: started\n        enabled: true\nEOF
> Check the syntax | check
text: --syntax-check parses the playbook without connecting to any host.
cmd: ansible-playbook site.yml --syntax-check
out: playbook: site.yml
> Preview with check and diff | eye
text: --check predicts what would change without changing anything. --diff shows file differences. Some modules cannot predict, so use it as a guide, not a guarantee.
cmd: ansible-playbook site.yml --check --diff
> Run it | rocket
text: Watch the task names go by. changed means the module changed something, ok means it was already right.
cmd: ansible-playbook site.yml
out: PLAY [Install and start Apache] ***\nTASK [Gathering Facts] ***\nok: [web1]\nTASK [Install Apache] ***\nchanged: [web1]\nTASK [Start and enable Apache] ***\nchanged: [web1]\nPLAY RECAP ***\nweb1 : ok=3 changed=2 unreachable=0 failed=0
> Run it again: idempotence | retry
text: The second run should report changed=0. If something always shows changed, it is probably a command or shell task, which cannot tell whether work is needed.
cmd: ansible-playbook site.yml
out: PLAY RECAP ***\nweb1 : ok=3 changed=0 unreachable=0 failed=0
> Verify the result | check
text: Check from the outside, the way a user would.
cmd: ansible web -b -m ansible.builtin.command -a "systemctl is-active apache2"
cmd: curl -sI http://web1.example.com | head -n 1

= ans-variables-facts | Variables and facts | 2 | sliders | Define variables, override them from the command line, and use facts that Ansible discovers about each host.
> Variables in a play | sliders
text: vars: defines values you can reuse with {{ name }}. Quote the whole value when it starts with a Jinja2 expression.
cmd: cat > vars-demo.yml <<'EOF'\n- name: Variables demo\n  hosts: web\n  vars:\n    greeting: Hello\n    port: 8080\n  tasks:\n    - name: Show variables\n      ansible.builtin.debug:\n        msg: "{{ greeting }} from {{ inventory_hostname }} on port {{ port }}"\nEOF
cmd: ansible-playbook vars-demo.yml
> Override from the command line | up
text: -e (extra vars) has the highest precedence of all. It is handy for one-off changes and for passing values from CI.
cmd: ansible-playbook vars-demo.yml -e "greeting=Hi port=9000"
cmd: ansible-playbook vars-demo.yml -e @extra.yml
> Magic variables | search
text: Ansible provides built-in variables. inventory_hostname is the name in the inventory, groups lists all groups and hostvars lets you read another host's variables.
cmd: ansible web -m ansible.builtin.debug -a "var=groups"
cmd: ansible web -m ansible.builtin.debug -a "var=inventory_hostname"
> Facts: what Ansible learns about a host | database
text: At the start of each play Ansible runs the setup module and stores the results under ansible_facts. Access them with ansible_facts['key'].
cmd: ansible web1.example.com -m ansible.builtin.setup -a "filter=ansible_distribution*"
cmd: ansible web1.example.com -m ansible.builtin.setup -a "filter=ansible_default_ipv4"
> Use facts in a task | check
text: Facts let one playbook adapt to the host, for example choosing the right package name.
cmd: cat > facts-demo.yml <<'EOF'\n- name: Facts demo\n  hosts: web\n  tasks:\n    - name: Show OS and memory\n      ansible.builtin.debug:\n        msg: "{{ ansible_facts['distribution'] }} {{ ansible_facts['distribution_version'] }} with {{ ansible_facts['memtotal_mb'] }} MB"\nEOF
cmd: ansible-playbook facts-demo.yml
> Set and register your own values | edit
text: set_fact creates a variable during the run. register stores a task's result so later tasks can use it.
cmd: cat > register-demo.yml <<'EOF'\n- name: Register demo\n  hosts: web\n  tasks:\n    - name: Read the kernel version\n      ansible.builtin.command: uname -r\n      register: kernel\n      changed_when: false\n    - name: Show it\n      ansible.builtin.debug:\n        msg: "Kernel is {{ kernel.stdout }}"\nEOF
cmd: ansible-playbook register-demo.yml

= ans-conditionals-loops | Conditionals and loops | 2 | filter | Run tasks only when a condition holds and repeat a task over a list.
> when: run a task conditionally | filter
text: when takes a Jinja2 expression without braces. The task is skipped, not failed, when the condition is false.
cmd: cat > when-demo.yml <<'EOF'\n- name: Conditional demo\n  hosts: all\n  tasks:\n    - name: Only on Debian family\n      ansible.builtin.debug:\n        msg: "This is a Debian-family host"\n      when: ansible_facts['os_family'] == "Debian"\nEOF
cmd: ansible-playbook when-demo.yml
> Combine conditions | layers
text: Use and, or and not, or give when a list, which means all items must be true.
cmd: cat > when-demo2.yml <<'EOF'\n- name: Several conditions\n  hosts: all\n  tasks:\n    - name: Big Ubuntu hosts only\n      ansible.builtin.debug:\n        msg: "match"\n      when:\n        - ansible_facts['distribution'] == "Ubuntu"\n        - ansible_facts['memtotal_mb'] > 1024\nEOF
> loop: repeat over a list | retry
text: loop runs the task once per item. The current item is {{ item }}. Giving the package module a list is faster than looping, but loop works for every module.
cmd: cat > loop-demo.yml <<'EOF'\n- name: Loop demo\n  hosts: web\n  become: true\n  tasks:\n    - name: Create several users\n      ansible.builtin.user:\n        name: "{{ item }}"\n        state: present\n      loop:\n        - alice\n        - bob\n        - carol\nEOF
cmd: ansible-playbook loop-demo.yml --check
> Loop over dictionaries | table
text: Each item can be a small dictionary. Access fields with item.name and item.groups.
cmd: cat > loop-demo2.yml <<'EOF'\n- name: Users with groups\n  hosts: web\n  become: true\n  tasks:\n    - name: Create users\n      ansible.builtin.user:\n        name: "{{ item.name }}"\n        groups: "{{ item.groups }}"\n      loop:\n        - { name: alice, groups: sudo }\n        - { name: bob, groups: users }\nEOF
> Conditions on results | check
text: Register a task result and branch on it. Use failed_when and changed_when to define what counts as a failure or a change.
cmd: cat > result-demo.yml <<'EOF'\n- name: React to a result\n  hosts: web\n  tasks:\n    - name: Is the app config present\n      ansible.builtin.stat:\n        path: /etc/myapp.conf\n      register: conf\n    - name: Warn when missing\n      ansible.builtin.debug:\n        msg: "config is missing"\n      when: not conf.stat.exists\nEOF

= ans-handlers | Handlers and notify | 2 | bell | Restart a service only when its configuration actually changed.
> The problem handlers solve | bell
text: If you restart Apache after every run, you cause needless downtime. You only want to restart when the configuration file really changed. Handlers do exactly that.
> A task that notifies | edit
text: When a task reports changed it can notify a handler by name. If the task reports ok, nothing is notified.
cmd: cat > handler-demo.yml <<'EOF'\n- name: Handler demo\n  hosts: web\n  become: true\n  tasks:\n    - name: Deploy the site config\n      ansible.builtin.copy:\n        src: mysite.conf\n        dest: /etc/apache2/conf-available/mysite.conf\n        mode: "0644"\n      notify: Reload Apache\n  handlers:\n    - name: Reload Apache\n      ansible.builtin.service:\n        name: apache2\n        state: reloaded\nEOF
> First run: the handler fires | play
text: The copy task changes the file, so the handler runs once at the end of the play, even if several tasks notified it.
cmd: echo "# demo" > mysite.conf
cmd: ansible-playbook handler-demo.yml
out: TASK [Deploy the site config] ***\nchanged: [web1]\nRUNNING HANDLER [Reload Apache] ***\nchanged: [web1]
> Second run: nothing happens | check
text: The file is identical, so the task is ok, the handler is skipped and the service is not touched.
cmd: ansible-playbook handler-demo.yml
> Run handlers earlier | up
text: Handlers normally wait until the end of the play. flush_handlers runs the pending ones immediately, which you need when a later task depends on the restart.
cmd: printf '    - name: Run pending handlers now\n      ansible.builtin.meta: flush_handlers\n' >> handler-demo.yml.snippet
note: Place this task between the tasks that need the service in its new state.

= ans-templates | Templates with Jinja2 | 2 | code | Generate configuration files from templates and variables, including loops and defaults.
> Why templates | code
text: Two servers rarely need identical config files. A template is a file with placeholders. Ansible fills them with each host's variables and writes the result.
> Create a template | edit
text: Template files end in .j2. {{ }} prints a value, and {% %} runs logic. The default filter supplies a fallback when a variable is missing.
cmd: mkdir -p templates
cmd: cat > templates/index.html.j2 <<'EOF'\n<h1>Welcome to {{ inventory_hostname }}</h1>\n<p>Port: {{ http_port | default(80) }}</p>\n<p>Managed by Ansible. Do not edit by hand.</p>\nEOF
> Use the template module | upload
text: The template module renders the file on the control node and copies the result. It is idempotent: it only reports changed when the output differs.
cmd: cat > template-demo.yml <<'EOF'\n- name: Render a page\n  hosts: web\n  become: true\n  tasks:\n    - name: Write index.html\n      ansible.builtin.template:\n        src: index.html.j2\n        dest: /var/www/html/index.html\n        mode: "0644"\nEOF
cmd: ansible-playbook template-demo.yml --check --diff
> Loops inside a template | retry
text: A for loop can build a list from your inventory, for example one line per web server.
cmd: cat > templates/hosts.j2 <<'EOF'\n{% for host in groups['web'] %}\n{{ hostvars[host]['ansible_host'] | default(host) }} {{ host }}\n{% endfor %}\nEOF
> Validate risky files | shield
text: The validate option runs a command on the rendered file before it replaces the real one. If it fails, the change is not applied. Use it for files that can lock you out, such as sudoers.
cmd: cat > validate-demo.yml <<'EOF'\n- name: Safe sudoers change\n  hosts: web\n  become: true\n  tasks:\n    - name: Allow the ops group\n      ansible.builtin.copy:\n        content: "%ops ALL=(ALL) NOPASSWD:ALL\\n"\n        dest: /etc/sudoers.d/ops\n        mode: "0440"\n        validate: /usr/sbin/visudo -cf %s\nEOF

> Run a slow job in the background | play
text: async says the task may run up to that many seconds. poll: 0 means "do not wait", so Ansible fires and moves on. Save the job id and check it later with async_status.
cmd: printf -- '- hosts: web\n  tasks:\n    - ansible.builtin.command: /usr/local/bin/long-backup.sh\n      async: 3600\n      poll: 0\n      register: job\n    - ansible.builtin.async_status:\n        jid: "{{ job.ansible_job_id }}"\n      register: res\n      until: res.finished\n      retries: 60\n      delay: 30\n' > async.yml
cmd: ansible-playbook async.yml --syntax-check
> Choose what counts as failure | warn
text: failed_when and changed_when decide the result yourself. A command that prints a warning but works can be told not to fail, and a read-only command should never report changed.
cmd: printf -- '- hosts: web\n  tasks:\n    - ansible.builtin.command: grep -c error /var/log/app.log\n      register: c\n      changed_when: false\n      failed_when: c.rc > 1\n' > rc.yml
cmd: ansible-playbook rc.yml --syntax-check
note: Use ignore_errors sparingly. It hides real problems; prefer failed_when with a precise rule.

= ans-molecule-test | Test a role with Molecule | 4 | flask | Create a role, run it in a throwaway container, check it with a verify step, and run the loop in CI.
> Install the tools | download
text: Molecule creates a test instance, applies your role, checks it is idempotent and runs verification. Containers make that fast. You need Docker or Podman on the machine.
cmd: python3 -m pip install --user molecule molecule-plugins[docker] ansible-lint
cmd: molecule --version
> Scaffold a role with a scenario | folder
text: ansible-galaxy init makes the role folders. molecule init scenario adds molecule/default with a platform file, a converge playbook and a verify playbook.
cmd: ansible-galaxy role init webtest
cmd: cd webtest
cmd: molecule init scenario default --driver-name docker
cmd: ls molecule/default
> Write the role and the check | edit
text: The role installs and starts nginx. verify.yml asserts what must be true afterwards. Tests state the expected result, not the steps.
cmd: printf -- '- name: Install nginx\n  ansible.builtin.package:\n    name: nginx\n    state: present\n' > tasks/main.yml
cmd: printf -- '- hosts: all\n  tasks:\n    - ansible.builtin.package_facts:\n    - ansible.builtin.assert:\n        that: "\x27nginx\x27 in ansible_facts.packages"\n' > molecule/default/verify.yml
> Run the whole loop | wf-loop
text: molecule test creates the container, converges, runs a second time to prove idempotence, verifies, then destroys everything. During development use converge and verify to stay fast.
cmd: molecule test
cmd: molecule converge && molecule verify
out: $ molecule test\nINFO     Running default > idempotence\nINFO     Idempotence completed successfully.\nINFO     Running default > verify\nINFO     Verifier completed successfully.
> Lint and run it in CI | gate
text: Run ansible-lint and molecule test on every pull request so a role cannot be merged broken.
cmd: ansible-lint .
cmd: printf 'name: role-test\non: [pull_request]\njobs:\n  molecule:\n    runs-on: ubuntu-latest\n    steps:\n      - uses: actions/checkout@v4\n      - run: pip install molecule molecule-plugins[docker] ansible-lint\n      - run: molecule test\n' > ../molecule-ci.yml
note: A pipeline that runs molecule test is the best evidence that a role is idempotent.

= ans-kubernetes-k8s | Manage Kubernetes objects with kubernetes.core.k8s | 4 | helm | Apply a namespace, a deployment and a service from a playbook, wait for readiness and clean up.
> Prepare the collection and access | download
text: The collection talks to the cluster API with the Python kubernetes client, using your kubeconfig. Check access first with kubectl.
cmd: ansible-galaxy collection install kubernetes.core
cmd: python3 -m pip install --user kubernetes
cmd: kubectl config current-context
cmd: kubectl get nodes
> Create a namespace | plus
text: The k8s module is declarative: state present creates or updates, absent deletes. Run it twice and the second run reports ok.
cmd: printf -- '- hosts: localhost\n  gather_facts: false\n  tasks:\n    - name: Namespace\n      kubernetes.core.k8s:\n        state: present\n        definition:\n          apiVersion: v1\n          kind: Namespace\n          metadata:\n            name: demo\n' > k8s.yml
cmd: ansible-playbook k8s.yml
> Deploy an application | rocket
text: Put the manifest in a template and fill in image and replica count from variables. wait makes the task finish only when the Deployment is available, so later tasks can rely on it.
cmd: printf -- '    - name: Deployment\n      kubernetes.core.k8s:\n        state: present\n        wait: true\n        wait_timeout: 120\n        definition:\n          apiVersion: apps/v1\n          kind: Deployment\n          metadata: {name: web, namespace: demo}\n          spec:\n            replicas: 2\n            selector: {matchLabels: {app: web}}\n            template:\n              metadata: {labels: {app: web}}\n              spec:\n                containers:\n                  - {name: web, image: nginx:1.27}\n' >> k8s.yml
cmd: ansible-playbook k8s.yml --check --diff
> Read state back | eye
text: k8s_info returns the live object so you can assert on it or print a field.
cmd: kubectl -n demo get deploy web
cmd: kubectl -n demo get pods -l app=web
out: $ kubectl -n demo get deploy web\nNAME   READY   UP-TO-DATE   AVAILABLE   AGE\nweb    2/2     2            2           41s
> Update and clean up | trash
text: Change the image tag in the variable and run again; Kubernetes rolls the pods. Delete with state absent, namespace last.
cmd: kubectl -n demo rollout status deploy/web
cmd: kubectl delete namespace demo
risk: 1
note: Test against a development cluster. Check the context before every run.
