= git-first-repo | Your first repo: from Hello World to a commit | 1 | commit | Create hello.txt, understand the file, then init, add, commit, status and log, watching each area change.
> Create a folder for the project | folder
text: A Git repository is an ordinary folder that Git watches. Make one and move into it.
cmd: mkdir -p ~/git-lab/hello-git
cmd: cd ~/git-lab/hello-git
cmd: pwd
> Create hello.txt with "Hello World" | edit
text: echo prints text and the > symbol sends it into a file, creating it. Git does not know about this file yet.
cmd: echo "Hello World" > hello.txt
cmd: ls
cmd: cat hello.txt
fx: new hello.txt
> Understand the file syntax | eye
text: A .txt file is plain text: characters grouped into lines, each line ending with a newline character. cat -e shows that hidden end of line as a $ sign. wc -l counts lines and wc -c counts bytes: 11 visible characters plus the newline make 12.
cmd: cat -e hello.txt
cmd: wc -l hello.txt
cmd: wc -c hello.txt
> git init: start tracking | gear
text: git init creates a hidden .git folder. That folder is the repository: it holds every commit, branch and setting. Delete .git and the history is gone, but your files stay.
cmd: git init
cmd: ls -a
fx: init
> git status: what does Git see? | search
text: status compares three things: your folder, the staging area and the last commit. hello.txt is listed as untracked, meaning it exists but Git is not recording it yet.
cmd: git status
> git add: stage the file | plus
text: add copies the current content of hello.txt into the staging area, a waiting room for the next commit. Run status again and the file moves to "Changes to be committed".
cmd: git add hello.txt
cmd: git status
fx: stage hello.txt
> git commit: save a snapshot | save
text: commit turns everything in the staging area into a permanent snapshot with a message. -m supplies the message so no editor opens. Write messages that finish the sentence "This commit will...".
cmd: git commit -m "Add hello.txt"
fx: commit "Add hello.txt"
> git log: read the history | doc
text: log lists commits, newest first. Each has a unique ID (a hash), an author, a date and the message. --oneline shows a short form.
cmd: git log --oneline
cmd: git log
> Change the file and look at the difference | diff
text: Edit the file again. status now says "modified" and diff shows exactly what changed: lines starting with + were added.
cmd: echo "Hello Git" >> hello.txt
cmd: git status --short
cmd: git diff
fx: edit hello.txt
> Complete the cycle: add, commit, log | retry
text: The everyday loop is edit, add, commit. Each pass adds one more snapshot to the history, and status ends clean.
cmd: git add hello.txt
cmd: git commit -m "Add greeting line"
cmd: git log --oneline
cmd: git status
fx: stage hello.txt ; commit "Add greeting line"

= git-three-areas | Working directory, staging area, repository | 1 | layers | The mental model behind every Git command: three places a change can live and the commands that move it between them.
> Start with one commit | commit
text: Make a repo with a single committed file so there is something to change.
cmd: mkdir -p ~/git-lab/areas && cd ~/git-lab/areas
cmd: git init
cmd: echo "v1" > notes.txt
cmd: git add notes.txt
cmd: git commit -m "Start notes"
fx: init ; new notes.txt ; stage notes.txt ; commit "Start notes"
> Edit the file: only the working directory changes | edit
text: Your edit exists only in the working directory. Nothing is staged and nothing is committed. git diff compares the working directory with the staging area.
cmd: echo "v2" >> notes.txt
cmd: git status --short
cmd: git diff
fx: edit notes.txt
> git add: copy the change to the staging area | plus
text: Now the change is staged. git diff shows nothing, because the working directory matches the staging area. git diff --staged compares the staging area with the last commit.
cmd: git add notes.txt
cmd: git diff
cmd: git diff --staged
fx: stage notes.txt
> Edit again: the same file in two places | layers
text: Editing after git add gives the file two versions. The staging area still holds v2, while the working directory has v3. The two letters in the short status show it: M in both columns.
cmd: echo "v3" >> notes.txt
cmd: git status --short
fx: edit notes.txt
> Commit saves only what is staged | save
text: Commit snapshots the staging area, not your folder. That is why v3 is still waiting as an unstaged change afterwards.
cmd: git commit -m "Add v2"
cmd: git status --short
cmd: git log --oneline
fx: commit "Add v2"
> Stage and commit the rest | check
text: git add -A stages every change in the project. Commit again and the working directory, staging area and repository all agree.
cmd: git add -A
cmd: git commit -m "Add v3"
cmd: git status
fx: stage notes.txt ; commit "Add v3"

= git-config-identity | Configure Git: identity, defaults and aliases | 1 | sliders | Tell Git who you are, set sensible defaults, add shortcuts and learn the three configuration levels.
> Set your name and email | user
text: Every commit records an author. Set it once with --global. Use the email you use on your Git host.
cmd: git config --global user.name "Alice Dev"
cmd: git config --global user.email "alice@example.com"
cmd: git config --global user.name
> Choose defaults | sliders
text: init.defaultBranch names the first branch of new repositories. pull.rebase false makes git pull merge, so its behaviour is explicit instead of a hint message.
cmd: git config --global init.defaultBranch main
cmd: git config --global pull.rebase false
cmd: git config --global --list
> Add aliases | tag
text: An alias is a shortcut stored in the configuration. Here st is a short status and lg is a compact history graph.
cmd: git config --global alias.st "status --short"
cmd: git config --global alias.lg "log --oneline --graph --decorate --all"
cmd: mkdir -p ~/git-lab/alias && cd ~/git-lab/alias && git init
cmd: echo hi > a.txt
cmd: git st
> Three levels of configuration | layers
text: system applies to every user, global to you, and local to one repository. The most specific level wins. Use --show-scope to see where a value comes from.
cmd: git config --local user.email "alice@work.example"
cmd: git config user.email
cmd: git config --show-scope user.email
> Edit and unset a value | edit
text: Values live in plain text files: ~/.gitconfig for global and .git/config for local. Remove a value you no longer want with --unset.
cmd: git config --local --unset user.email
cmd: git config user.email
cmd: cat .git/config

= git-status-diff | Read status and diff like a pro | 1 | diff | Modified, new, deleted and untracked files in the long and short status, and the four useful forms of diff.
> A repo with two files | folder
text: Create two committed files so there is something to change.
cmd: mkdir -p ~/git-lab/sd && cd ~/git-lab/sd
cmd: git init
cmd: echo "alpha" > a.txt
cmd: echo "beta" > b.txt
cmd: git add .
cmd: git commit -m "Add a and b"
fx: init ; new a.txt ; new b.txt ; stage a.txt ; stage b.txt ; commit "Add a and b"
> Modify one file, delete one, add one | edit
text: Three kinds of change at once: a.txt is modified, b.txt is deleted and c.txt is brand new.
cmd: echo "alpha two" >> a.txt
cmd: rm b.txt
cmd: echo "gamma" > c.txt
cmd: git status
fx: edit a.txt ; del b.txt ; new c.txt
> The short status | table
text: Two columns before each name: the left is the staging area and the right is the working directory. M modified, D deleted and ?? untracked. A blank means no change in that column.
cmd: git status --short
> git diff shows the content change | diff
text: diff lists changed lines for tracked files only. Lines starting with - were removed, + were added. The untracked c.txt does not appear.
cmd: git diff
> A summary instead of the full patch | chart
text: --stat shows files and the number of changed lines and --name-only lists just the names, handy for scripts.
cmd: git diff --stat
cmd: git diff --name-only
> Stage some changes and compare again | plus
text: After staging a.txt, plain diff no longer shows it. Use --staged for what the next commit will contain.
cmd: git add a.txt
cmd: git diff --name-only
cmd: git diff --staged
fx: stage a.txt

= git-undo-changes | Undo mistakes safely | 2 | undo | Discard edits, unstage files, undo a commit with revert and move the branch back with reset --soft.
> A repo with one good commit | commit
text: Start from a clean state with one commit, so each undo has a known target.
cmd: mkdir -p ~/git-lab/undo && cd ~/git-lab/undo
cmd: git init
cmd: echo "good line" > app.txt
cmd: git add app.txt
cmd: git commit -m "Add app.txt"
fx: init ; new app.txt ; stage app.txt ; commit "Add app.txt"
> Throw away an uncommitted edit | trash
text: git restore puts the file back to the last committed (or staged) version. The edit is gone for good because Git never saved it.
cmd: echo "oops" >> app.txt
cmd: cat app.txt
cmd: git restore app.txt
cmd: cat app.txt
risk: 1
fx: edit app.txt ; restore app.txt
> Unstage a file | minus
text: git restore --staged removes a file from the staging area but keeps your edit in the working directory.
cmd: echo "not ready" >> app.txt
cmd: git add app.txt
cmd: git status --short
cmd: git restore --staged app.txt
cmd: git status --short
fx: edit app.txt ; stage app.txt ; unstage app.txt
> Clean up the leftover edit | trash
text: The edit is still in the working directory. Discard it to get back to a clean state.
cmd: git restore app.txt
cmd: git status --short
risk: 1
fx: restore app.txt
> Undo a commit with revert | undo
text: revert makes a new commit that cancels an old one. History is kept, so it is safe even after you have shared the commit.
cmd: echo "bad change" >> app.txt
cmd: git commit -am "Add bad change"
cmd: git revert --no-edit HEAD
cmd: git log --oneline
fx: edit app.txt ; stage app.txt ; commit "Add bad change" ; revert "Revert: Add bad change"
> Undo a commit that is not shared: reset --soft | up
text: reset --soft moves the branch back one commit and leaves the changes staged, ready to commit again with a better message. Only do this for commits nobody else has.
cmd: echo "small step" >> app.txt
cmd: git commit -am "Too early commit"
cmd: git reset --soft HEAD~1
cmd: git status --short
cmd: git commit -m "Add small step properly"
cmd: git log --oneline
fx: edit app.txt ; stage app.txt ; commit "Too early commit" ; reset soft 1 ; commit "Add small step properly"
> The safety net: reflog | search
text: reflog records every place HEAD has pointed, including commits you thought were lost. It is how you recover from most mistakes.
cmd: git reflog -n 6

= git-gitignore | Keep junk out with .gitignore | 1 | ban | Ignore logs and build output, find out why a file is ignored and stop tracking a file that was committed by mistake.
> A project with files you do not want | folder
text: A script plus a log file and a build folder. Git lists all three as untracked.
cmd: mkdir -p ~/git-lab/ignore/build && cd ~/git-lab/ignore
cmd: git init
cmd: echo "print('hi')" > app.py
cmd: echo "debug line" > debug.log
cmd: echo "binary" > build/app.bin
cmd: git status --short
fx: init ; new app.py ; new debug.log ; new build/app.bin
> Create .gitignore | edit
text: One pattern per line. *.log matches any file ending in .log and a trailing slash matches a folder. Now only the useful files remain untracked.
cmd: echo "*.log" > .gitignore
cmd: echo "build/" >> .gitignore
cmd: cat .gitignore
cmd: git status --short
fx: new .gitignore ; del debug.log ; del build/app.bin
> Ask why a file is ignored | search
text: check-ignore -v prints the exact rule and line that matched. It is the fastest way to debug an ignore pattern.
cmd: git check-ignore -v debug.log build/app.bin
> Commit the right files | save
text: Commit the source and the .gitignore itself, so everyone shares the same rules.
cmd: git add .gitignore app.py
cmd: git commit -m "Add app and gitignore"
cmd: git status --short
fx: stage .gitignore ; stage app.py ; commit "Add app and gitignore"
> Fix a file that is already tracked | warn
text: Ignore rules only affect untracked files. If you committed .env by mistake, adding it to .gitignore is not enough. git rm --cached stops tracking it but keeps your local copy.
cmd: echo "SECRET=1" > .env
cmd: git add -f .env
cmd: git commit -m "Oops: add .env"
cmd: echo ".env" >> .gitignore
cmd: git rm --cached .env
cmd: git commit -am "Stop tracking .env"
cmd: git status --short
note: The secret is still in the older commit. If it was ever pushed, treat it as leaked and rotate it.
fx: new .env ; stage .env ; commit "Oops: add .env" ; edit .gitignore ; del .env ; stage .gitignore ; commit "Stop tracking .env"

= git-branching | Branching: work on a copy without breaking main | 1 | branch | Create, switch, compare and delete branches, and see that each branch has its own files.
> Start with one commit on main | commit
text: A branch is just a movable label on a commit. Create a repo with one commit.
cmd: mkdir -p ~/git-lab/branching && cd ~/git-lab/branching
cmd: git init
cmd: echo "home page" > index.txt
cmd: git add index.txt
cmd: git commit -m "Add home page"
fx: init ; new index.txt ; stage index.txt ; commit "Add home page"
> Create a branch and switch to it | branch
text: switch -c creates a branch and moves to it in one step. The star marks the branch you are on.
cmd: git switch -c feature/login
cmd: git branch
fx: switch feature/login
> Commit on the branch | save
text: This commit belongs to feature/login only. main has not moved.
cmd: echo "login page" > login.txt
cmd: git add login.txt
cmd: git commit -m "Add login page"
cmd: git log --oneline --graph --all
fx: new login.txt ; stage login.txt ; commit "Add login page"
> Switch back: your files change | swap
text: Git rewrites your working directory to match the branch. On main the login file does not exist. Switch back and it returns.
cmd: git switch main
cmd: ls
cmd: git switch feature/login
cmd: ls
fx: switch main ; switch feature/login
> Compare the branches | diff
text: main..feature/login lists the commits on the feature branch that main does not have yet.
cmd: git branch -v
cmd: git log main..feature/login --oneline
> Rename, merge and delete | trash
text: -d deletes a branch only when its work is merged, and refuses otherwise. That refusal is a safety feature. Merge first, then delete.
cmd: git branch -m feature/login feature/sign-in
cmd: git switch main
cmd: git branch -d feature/sign-in
cmd: git merge feature/sign-in
cmd: git branch -d feature/sign-in
note: git branch -D deletes without checking. Use it only when you are sure the work is not needed.
fx: switch main ; merge feature/sign-in

= git-merge | Merging: fast-forward and merge commits | 2 | merge | See the two kinds of merge: a simple fast-forward and a true merge commit with two parents.
> Set up the base | commit
text: One commit on main to start from.
cmd: mkdir -p ~/git-lab/merge && cd ~/git-lab/merge
cmd: git init
cmd: echo "base" > base.txt
cmd: git add base.txt
cmd: git commit -m "Add base"
fx: init ; new base.txt ; stage base.txt ; commit "Add base"
> A branch that main has not left behind | branch
text: Create feature-a and commit once. Because main did not change meanwhile, main can simply catch up.
cmd: git switch -c feature-a
cmd: echo "a" > a.txt
cmd: git add a.txt
cmd: git commit -m "Add a"
cmd: git switch main
fx: switch feature-a ; new a.txt ; stage a.txt ; commit "Add a" ; switch main
> Fast-forward merge | up
text: No new commit is needed. Git just moves the main label forward to the same commit as feature-a. History stays a straight line.
cmd: git merge feature-a
cmd: git log --oneline --graph
fx: merge feature-a
> Make the branches diverge | swap
text: Now give feature-b one commit and main a different one. Neither branch contains the other's work.
cmd: git switch -c feature-b
cmd: echo "b" > b.txt
cmd: git add b.txt
cmd: git commit -m "Add b"
cmd: git switch main
cmd: echo "main change" > main.txt
cmd: git add main.txt
cmd: git commit -m "Add main change"
fx: switch feature-b ; new b.txt ; stage b.txt ; commit "Add b" ; switch main ; new main.txt ; stage main.txt ; commit "Add main change"
> A true merge creates a merge commit | merge
text: Git combines the two lines of work into a new commit that has two parents. -m gives it a message so no editor opens.
cmd: git merge feature-b -m "Merge feature-b"
cmd: git log --oneline --graph
fx: merge feature-b
> Read the graph | eye
text: The graph shows the fork and the join. Use --parents to see the two parent hashes of the merge commit, and -m with show to see changes against each parent.
cmd: git log --oneline --graph --all
cmd: git show --no-patch --pretty=%P HEAD

= git-merge-conflict | Resolve a merge conflict | 2 | warn | Make two branches edit the same line, read the conflict markers, choose the result and finish the merge.
> A shared starting file | commit
text: One file with one line, committed on main.
cmd: mkdir -p ~/git-lab/conflict && cd ~/git-lab/conflict
cmd: git init
cmd: echo "greeting: hello" > app.txt
cmd: git add app.txt
cmd: git commit -m "Add greeting"
fx: init ; new app.txt ; stage app.txt ; commit "Add greeting"
> Change the line on a branch | branch
text: On feature, rewrite the line one way.
cmd: git switch -c feature
cmd: echo "greeting: hello team" > app.txt
cmd: git commit -am "Greet the team"
fx: switch feature ; edit app.txt ; stage app.txt ; commit "Greet the team"
> Change the same line on main | swap
text: On main, rewrite the same line a different way. Git cannot know which one you want.
cmd: git switch main
cmd: echo "greeting: hello world" > app.txt
cmd: git commit -am "Greet the world"
fx: switch main ; edit app.txt ; stage app.txt ; commit "Greet the world"
> Merge: Git stops and reports a conflict | warn
text: The merge pauses with the file marked UU, unmerged on both sides. Nothing is lost. You are in the middle of a merge and can still cancel it with git merge --abort.
cmd: git merge feature
cmd: git status --short
fx: conflict app.txt
> Read the conflict markers | eye
text: Git wrote both versions into the file. Between <<<<<<< and ======= is your side (HEAD), and between ======= and >>>>>>> is the other branch. Edit the file to the final text and delete all three marker lines.
cmd: cat app.txt
> Resolve, stage and finish the merge | check
text: Write the result you want, mark the file resolved with git add, then commit to complete the merge.
cmd: echo "greeting: hello team and world" > app.txt
cmd: git add app.txt
cmd: git commit -m "Merge feature: combine greetings"
cmd: git log --oneline --graph
fx: resolve app.txt ; merge feature

= git-rebase | Rebase: a straight line of history | 3 | retry | Move a branch on top of the latest main, compare it with merging and learn when never to rebase.
> Base commit | commit
text: Start with one commit on main.
cmd: mkdir -p ~/git-lab/rebase && cd ~/git-lab/rebase
cmd: git init
cmd: echo "base" > base.txt
cmd: git add base.txt
cmd: git commit -m "Add base"
fx: init ; new base.txt ; stage base.txt ; commit "Add base"
> Two commits on a feature branch | branch
text: The feature work starts from the base commit.
cmd: git switch -c feature
cmd: echo "one" > f1.txt
cmd: git add f1.txt
cmd: git commit -m "Feature part 1"
cmd: echo "two" > f2.txt
cmd: git add f2.txt
cmd: git commit -m "Feature part 2"
fx: switch feature ; new f1.txt ; stage f1.txt ; commit "Feature part 1" ; new f2.txt ; stage f2.txt ; commit "Feature part 2"
> main moves on | swap
text: Meanwhile someone adds a commit to main, so the branches have diverged.
cmd: git switch main
cmd: echo "hotfix" > hotfix.txt
cmd: git add hotfix.txt
cmd: git commit -m "Add hotfix"
cmd: git log --oneline --graph --all
fx: switch main ; new hotfix.txt ; stage hotfix.txt ; commit "Add hotfix"
> Rebase feature onto main | retry
text: Rebase replays your feature commits on top of the latest main. They get new IDs because their parent changed. The history becomes a straight line with no merge commit.
cmd: git switch feature
cmd: git rebase main
cmd: git log --oneline --graph --all
fx: switch feature ; rebase main
> Fast-forward main | up
text: Now main is an ancestor of feature, so merging is a plain fast-forward.
cmd: git switch main
cmd: git merge feature
cmd: git log --oneline --graph
fx: switch main ; merge feature
> The golden rule | shield
text: Rebase rewrites commits. Only rebase work that is still local to you. Never rebase commits that others have pulled, because their copies will no longer match yours. If you must update a branch you already pushed, use git push --force-with-lease and tell the team.
note: When in doubt, merge. It never rewrites history.

= git-collaborate | Project: two teammates, one remote | 3 | users | Simulate Alice and Bob: a rejected push, pull --rebase and a clean shared history.

= git-stash | Stash work in progress | 2 | package | Park half-finished changes, do something urgent, then bring them back.

text: Start with one committed file.

text: You are mid-change: a modified tracked file and a brand new untracked one.

cmd: git stash list

= git-force-push-recovery | Recover from a bad force push | 3 | undo | See why a plain push is rejected, use --force-with-lease, and bring back a commit that was overwritten.

text: A bare repository acts as the server. Push three commits.
cmd: mkdir -p ~/git-lab/fp

text: A reset throws away the last commit and a new commit takes its place. History now differs from the server's, so a normal push is refused to protect everyone else's work.

cmd: echo "replacement" >> app.txt

text: --force-with-lease overwrites the server only if it still matches what you last fetched. If a teammate pushed meanwhile it refuses. Plain --force skips that check.

cmd: git log --oneline

note: Never force-push a shared branch such as main. Protect it on the server so force pushes are blocked.

text: Nothing is deleted at once. Your remote-tracking branch remembers its previous position, and the reflog lists where HEAD has been.

cmd: git rev-parse origin/main@{1}

text: Create a branch at the old position so the commit is reachable again, then decide whether to cherry-pick it or restore the branch.
cmd: git branch rescue origin/main@{1}

note: Servers delete unreachable commits during garbage collection, so recover soon.
