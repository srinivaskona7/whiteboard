AWS EC2 · Linux boot chain

How a Linux instance boots on EC2

Eight stages from RunInstances to first-boot configuration, laid out by the layer that owns each hand-off — the AWS control plane, the hypervisor, firmware, the kernel, and userspace.

The two halves

  • Steps 1–2 run entirely in the AWS control plane — nothing of yours executes yet
  • The AMI's root volume is cloned and attached before any guest instruction runs
  • Step 3 is the first code that executes inside your instance

Where boots stall

  • GRUB — missing or corrupt /boot, or a stale root=UUID
  • Kernel — initramfs with no ENA or NVMe driver, so the root device never appears
  • cloud-init — no route to 169.254.169.254, or an IMDSv2 token refused

Where to look

  • Console → Actions → Monitor and troubleshoot → Get system log
  • Serial console, for GRUB and early kernel output
  • Status checks: instance reachability first, then system

Step by step · internals

What actually happens in each stage

The diagram is the map; this is the wiring. Each stage below names what runs, where the boundary is crossed, which paths and parameters decide the outcome, and the failure signature you will actually see when it breaks.

01
EC2
control plane

Instance request

An authenticated API call creates intent, not hardware. Everything after this is the control plane trying to make the intent true.

  • RunInstances is SigV4-signed against the regional EC2 endpoint. The response returns an i-… id immediately in state pending — the launch itself is asynchronous.
  • IAM evaluates SCPs, identity policy, permission boundary and resource policy. ec2:RunInstances also needs rights on the referenced resources: the AMI, its snapshot, the subnet, security groups, key pair, and ec2:CreateVolume for EBS-backed AMIs.
  • Fields that change the boot later: ImageId, InstanceType, BlockDeviceMappings (root size, type, DeleteOnTermination), UserData (≤ 16 KB, base64), MetadataOptions (HttpTokens=required, HttpPutResponseHopLimit), IamInstanceProfile.
  • Validation here is synchronous and cheap: AMI state and visibility, AZ capacity for the type, free IPs in the subnet, vCPU service quota, EBS attachment limits.
Artifacts
i-… id · pending state · resolved launch template version
Fails as
InsufficientInstanceCapacity, VcpuLimitExceeded, InvalidAMIID.NotFound, UnauthorizedOperation — all before any hardware exists.
02
Nitro
hypervisor

Host placement and provisioning

The placement service picks the physical host; the Nitro host agent then builds a guest around your AMI's disk image.

  • Placement bin-packs against free capacity in the AZ, honouring tenancy (shared, dedicated, host). Snapshots are regional but volumes are AZ-scoped — a snapshot not yet resident in the AZ is copied from S3 before first use, which is why a first launch in a new AZ is slower.
  • vCPUs are allocated as hyperthreads on physical cores plus a fixed memory reservation. The instance type decides how many Nitro PCIe functions you get.
  • Devices are presented as plain PCIe: the ENA network adapter, an NVMe controller for EBS, and instance-store NVMe when the type has it. Nitro moves the I/O off-box, so the guest never sees a SATA/AHCI controller.
  • The root EBS volume is created from the AMI snapshot and attached. The guest sees /dev/nvme0n1 while the API still calls it /dev/xvda — a naming compatibility shim, not a device.
  • The volume's first sector must carry a valid MBR/GPT with the active flag set, or the firmware finds nothing to execute.
Artifacts
root volume attaching → attached · PCIe device map · DMI/SMBIOS identity
Fails as
stuck in pending then shutting-down, or Client.VolumeLimitExceeded. A blank or garbage root volume gives “No bootable device” at step 3.
03
Firmware

UEFI and device bring-up

Nitro guests boot with UEFI, not BIOS. The firmware is AWS's OVMF-derived build — there is no POST in the sense you would find on a laptop.

  • Execution walks SEC → PEI → DXE. DXE enumerates PCIe and publishes the ACPI tables (DSDT, MADT, SRAT) plus DMI/SMBIOS — exactly what dmidecode reports later: instance type, AZ, system UUID.
  • The NVMe and ENA option ROMs initialise here, which is why disks and the NIC exist before any OS driver loads.
  • Boot order is resolved from the AMI's UEFI boot entries (HD(), CDROM()); the default is the root volume. --uefi-data can register a custom entry, and Secure Boot verifies the loader's PE signature before running it.
  • Firmware reads the GPT, finds the EFI System Partition, loads \EFI\BOOT\BOOTX64.EFI or \EFI\amazon\grubx64.efi, then calls ExitBootServices(). From that instant the firmware is gone and the OS owns the machine.
Artifacts
ACPI + DMI tables · ESP contents · boot entry in NVRAM
Fails as
“No bootable device” on the serial console, an empty system log, or the instance stopping itself. A Xen-era AMI on Nitro shows a SeaBIOS screen and then hangs.
04
Firmware
→ loader

Boot loader

GRUB's only job is to pick a kernel and hand it a command line. On EC2, that command line is where most boot bugs are written.

  • grubx64.efi loads its modules and reads grub.cfg — /boot/grub2/grub.cfg on Amazon Linux and RHEL, /boot/grub/grub.cfg on Ubuntu. It is generated from /etc/default/grub plus /etc/grub.d/* by grub2-mkconfig or update-grub.
  • Each entry is a linux + initrd pair: it decompresses vmlinuz (a bzImage — 16-bit setup header plus a compressed 64-bit payload) and stages initramfs in memory.
  • Parameters that matter on EC2: root=UUID=…, console=tty0 console=ttyS0,115200n8 (this is what makes output reach the system log and serial console), ro, nvme_core.io_timeout=4294967295 to survive EBS latency spikes, crashkernel= for kdump, ima_policy= for measured boot.
  • Control transfers to the kernel's EFI stub. There is no boot sector and no int 19h.
menuentry 'Amazon Linux (6.1.x)' --class fedora {
    linux /vmlinuz-6.1.xx root=UUID=6f1a… ro console=tty0 \
          console=ttyS0,115200n8 nvme_core.io_timeout=4294967295
    initrd /initramfs-6.1.xx.img
}
Artifacts
vmlinuz-* · initramfs-* · /boot/grub2/grub.cfg · /etc/default/grub
Fails as
error: file '/vmlinuz-…' not found, unknown filesystem, or the grub> rescue prompt. Repair from a rescue instance with chroot then grub2-install / grub2-mkconfig.
05
Linux
kernel

Kernel load ★

The kernel boots twice: once into the initramfs, then into the real root. This is the first stage where a broken AMI fails quietly instead of loudly.

  • The EFI stub decompresses into long mode. start_kernel() builds the GDT/IDT and paging, then parses boot_params — the command line handed over by GRUB.
  • Bring-up order: memblock → buddy allocator → SMP via APIC INIT-SIPI → ACPI parse → timers (TSC/HPET) → scheduler → do_initcalls() at levels early, core, postcore, arch, subsys, fs, device, late.
  • Built-in and initramfs drivers probe in parallel. On Nitro, nvme, nvme_core, ena and xfs/ext4 must be reachable here, or the root device never appears.
  • Hardware stays fully virtual: no SMBIOS string matching or ACPI DMI quirks. PCIe IDs and the ACPI tables are all the kernel sees.
  • Finally init/main.c unpacks the cpio into the tmpfs rootfs, frees init memory, and executes /init.
Artifacts
dmesg · /proc/cmdline · /sys/firmware/acpi · uname -r
Fails as
VFS: Unable to mount root fs on unknown-block(0,0), Kernel panic - not syncing: No working init found, or “elastic network adapter not found” — the classic Xen-built AMI launched on Nitro.
06
Linux
kernel

Root pivot

The initramfs is a life-support shell: mount the real root, then replace itself with it.

  • /init is dracut's shell script (on Ubuntu, initramfs-tools plus busybox). It mounts /proc, /sys, /dev, coldplugs udev with udevadm trigger, loads modules-load.d entries and waits for root=UUID= to resolve under /dev/disk/by-uuid/.
  • Optional stacks activate here in order: dm-crypt/LUKS, LVM (vgchange -ay), multipath, iSCSI/NBD, then fsck according to fsck.mode=.
  • Root is mounted read-only at /sysroot, /dev /proc /sys are moved over, and switch_root performs pivot_root plus an unlink of the initramfs, reclaiming its memory and replacing PID 1.
  • Rebuild commands: dracut -f --kver $(uname -r) --add-drivers "ena nvme" on RHEL/AL, or update-initramfs -u -k all on Debian/Ubuntu.
Artifacts
/sysroot · /run/initramfs · initramfs-*.img
Fails as
A dracut emergency shell, or an endless “Waiting for device /dev/disk/by-uuid/…”. Both mean the initramfs cannot see the volume — almost always a missing ena/nvme/xfs module, or a stale UUID after a snapshot restore.
07
systemd

PID 1 and the unit graph

Boot on the real root is a dependency graph, not a sequence of runlevels.

  • /usr/lib/systemd/systemd becomes PID 1, re-execs into a clean namespace, mounts /run, and systemd-fstab-generator turns /etc/fstab into .mount and .swap units.
  • Ordering is a DAG: After=/Before= control sequence, Requires=/Wants= control failure propagation. Socket activation (ssh.socket) lets services come up in parallel.
  • The EC2 ordering in practice: systemd-remount-fs (root read-write) → local-fs.target → cloud-init-local.service → network.target → network-online.target → cloud-init.service → sshd.service → multi-user.target.
  • systemd-analyze splits the boot into firmware, loader, kernel and userspace; critical-chain shows what is actually on the slow path.
Artifacts
journalctl -b · systemctl list-units --failed · systemd-analyze blame
Fails as
“Reached target” never prints and SSH never answers. A unit with After= on a target that never activates blocks everything queued behind it.
08
cloud-init

First-boot configuration

The instance is already running by now. cloud-init is what makes it yours: hostname, keys, packages, user-data.

  • Four ordered units: cloud-init-local (before network, local datasource) → cloud-init (network up, DatasourceEc2) → cloud-config (modules: users-groups, ssh, write-files) → cloud-final (runcmd, package installs).
  • Metadata comes from the link-local 169.254.169.254, never DNS. IMDSv2 requires a PUT /latest/api/token with X-aws-ec2-metadata-token-ttl-seconds; every subsequent GET carries the session token.
  • user-data is dispatched by content: #cloud-config YAML runs modules, a #! shebang runs as a script, MIME multipart runs every part, gzip is decompressed. The ceiling is 16 KB.
  • Also seeded here: /etc/hostname (ip-10-0-0-5), authorized_keys from the key pair, regenerated SSH host keys, and IAM role credentials from /latest/meta-data/iam/security-credentials/<role>.
  • EC2 health is then two checks: instance status (hypervisor reachability) and system status (OS and ENA responding). Both green gives 2/2 checks passed.
TOKEN=$(curl -sX PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/
Artifacts
/var/lib/cloud · /var/log/cloud-init-output.log · /run/cloud-init/result.json
Fails as
cloud-init status --long reporting error after a two-minute metadata timeout — a missing route, IMDS disabled, or HttpPutResponseHopLimit=1 breaking containers.

Reference

Technical terms

TermWhat it means in this chain
AMIAmazon Machine Image — root volume snapshots plus launch metadata: architecture, block device mapping, UEFI boot data, default user-data.
SnapshotBlock-level point-in-time copy of an EBS volume, stored in S3. Regional; a volume created from it is AZ-scoped.
EBSElastic Block Store — network-attached block storage, presented to the guest as an NVMe device.
NitroAWS's offloaded virtualisation platform: network, storage and management I/O run on dedicated cards rather than in the hypervisor's software path.
ENAElastic Network Adapter — the PCIe NIC at 10–100 Gbps. Needs the ena driver present in the kernel or initramfs.
NVMeNon-Volatile Memory Express — the PCIe storage protocol EBS volumes speak. /dev/xvda is only an API alias.
UEFI / OVMFUnified Extensible Firmware Interface; OVMF is the open-source reference implementation AWS builds its guest firmware from.
ESPEFI System Partition — a FAT32 partition holding the .efi loaders that firmware executes.
GPTGUID Partition Table — the partition map firmware reads. MBR is the legacy alternative.
GRUB 2The boot loader. Reads grub.cfg, loads kernel and initramfs, and supplies the kernel command line.
bzImage / vmlinuzThe compressed kernel image: a 16-bit setup header plus a compressed 64-bit payload whose EFI stub decompresses itself.
initramfsA cpio archive unpacked into an in-memory tmpfs. Its /init mounts the real root before handing over. initrd is the older block-device form of the same idea.
dracutThe initramfs generator on RHEL and Amazon Linux. initramfs-tools does the same job on Debian and Ubuntu.
pivot_root / switch_rootThe syscall, and dracut's wrapper, that swap the initramfs root for the real root and replace PID 1.
systemd unit / targetPID 1 and its object model: a unit is one managed thing (.service, .mount, .socket); a target groups units and is not a runlevel.
cloud-initFirst-boot configuration agent — four ordered systemd units that read metadata and user-data and apply them.
IMDS / IMDSv2Instance Metadata Service on 169.254.169.254. v2 requires a session token obtained by PUT, which defends against SSRF.
user-dataThe ≤ 16 KB blob passed to RunInstances: cloud-config YAML, a script, or MIME multipart.
Status checksInstance status = hypervisor reachability. System status = OS and ENA responsiveness. 2/2 is healthy.
Serial consoleOut-of-band text I/O via console=ttyS0 — the only way to see firmware, GRUB and early kernel output.
