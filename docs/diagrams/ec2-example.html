Two principals, one command

01

The two principals

Both are IAM users in the same account, so both can sign in and both reach the same regional endpoint. The only difference is one attached policy.

Why “no permissions” is not “no access to the console”. Authentication and authorisation are separate steps. Signing in only proves the credentials are real. Every subsequent API call is authorised independently — which is why the non-admin can log in and still see an empty, broken console.

02

Where the two paths split

Everything before IAM is identical for both users: same endpoint, same signature check, same request body. The fork happens at one question — is there a policy that allows this?

Note where the arrow terminates. The non-admin never reaches the control plane, so no instance id is created, no volume is reserved and nothing is billed. Authorisation is evaluated before any resource is touched — a denied call has zero side effects.

03

Configuring it, in order

Eight steps. Steps 1–5 build the world the request runs in; step 6 creates the two principals; steps 7–8 send the identical call from each. Run them with an admin profile, because everything here is account configuration.

01Region

Pin the region to us-east-1

Region is a client-side setting, not a permission. Both profiles must point at us-east-1 or you will be comparing two different request paths without noticing.

aws configure set region us-east-1 --profile admin
aws configure set region us-east-1 --profile dev

aws sts get-caller-identity --profile admin
{ "UserId": "AIDAEXAMPLEUSERID", "Account": "123456789012", "Arn": "arn:aws:iam::123456789012:user/admin-alice" }

A wrong region does not produce a permission error. It produces InvalidAMIID.NotFound, because every AMI id is valid in exactly one region — which is why “it works in eu-west-1” is a region bug, not an IAM bug.

02Network

Confirm the default VPC exists

Accounts created after 2013 get one default VPC per region: 172.31.0.0/16, one /20 subnet in every AZ, an internet gateway, a main route table sending 0.0.0.0/0 to it, and public IP auto-assignment on. It can be deleted — and once deleted, RunInstances without --subnet-id fails.

aws ec2 describe-vpcs --filters Name=is-default,Values=true \
  --query 'Vpcs[0].[VpcId,CidrBlock]' --output text
vpc-0a1b2c3d4e5f60718 172.31.0.0/16

Empty output means there is no default VPC. Recreate it, then capture the three ids the launch will need:

aws ec2 create-default-vpc

VPC=$(aws ec2 describe-vpcs --filters Name=is-default,Values=true \
        --query 'Vpcs[0].VpcId' --output text)
SUBNET=$(aws ec2 describe-subnets --filters Name=vpc-id,Values=$VPC \
        --query 'Subnets[0].SubnetId' --output text)
SG=$(aws ec2 describe-security-groups --filters Name=vpc-id,Values=$VPC \
        Name=group-name,Values=default \
        --query 'SecurityGroups[0].GroupId' --output text)
03Access

Create a key pair in the same region

Key pairs are regional objects, not account-wide. A key created in eu-west-1 does not exist in us-east-1, and the launch fails with InvalidKeyPair.NotFound.

aws ec2 create-key-pair --key-name lab-key --key-type ed25519 \
  --query KeyMaterial --output text > lab-key.pem
chmod 400 lab-key.pem

You can skip keys entirely and use SSM Session Manager or EC2 Instance Connect instead — both need an IAM instance profile, but neither needs an inbound port 22 rule.

04Firewall

Open SSH on the default security group

This is the step everyone forgets. The default security group has exactly one inbound rule: all traffic from members of itself. There is no rule allowing your laptop. Launch into it and you get a running instance you cannot connect to.

aws ec2 authorize-security-group-ingress --group-id $SG \
  --protocol tcp --port 22 --cidr 203.0.113.10/32

Use your own address, not 0.0.0.0/0. If the rule is missing, the symptom is not an AWS error at all — it is an SSH connection that times out, which is why it gets misdiagnosed as a broken boot.

05Image

Resolve an AMI id for us-east-1

AMI ids are region-specific, so never hard-code one from a tutorial. The SSM public parameter always points at the current Amazon Linux 2023 build in whatever region your client is set to.

AMI=$(aws ssm get-parameter \
  --name /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 \
  --query Parameter.Value --output text)
echo $AMI
ami-0abc123def456789a

The AMI also supplies the defaults you did not specify: the root volume size and type, the partition layout, the UEFI boot entry and the initial user account (ec2-user on Amazon Linux, ubuntu on Ubuntu).

06Identity

Create the two principals

Both are IAM users. The only asymmetry is the attached policy — and the second one is deliberately left empty.

aws iam create-user --user-name admin-alice
aws iam attach-user-policy --user-name admin-alice \
  --policy-arn arn:aws:iam::aws:policy/AdministratorAccess
aws iam create-access-key --user-name admin-alice

aws iam create-user --user-name dev-bob
aws iam create-access-key --user-name dev-bob
# no attach-user-policy, no group, no inline policy

One caveat before you trust AdministratorAccess. That policy means “everything, allowed” — but it is still an identity policy. If this account sits inside an AWS Organization, a Service Control Policy above it can remove actions even from an administrator. An admin in a member account is not the same as an admin in the management account.

07Admin

Launch as the admin

aws ec2 run-instances --profile admin \
  --image-id $AMI --instance-type t3.micro --count 1 \
  --key-name lab-key --security-group-ids $SG --subnet-id $SUBNET \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=admin-demo}]' \
  --query 'Instances[0].[InstanceId,State.Name]' --output text
i-0abc123def4567890 pending

Note what came back: an id and the word pending. No IP, no host. Give it 30–90 seconds, then:

aws ec2 describe-instance-status --instance-ids i-0abc123def4567890 \
  --query 'InstanceStatuses[0].[InstanceState.Name,InstanceStatus.Status,SystemStatus.Status]' \
  --output text
running ok ok

Two ok values are the 2/2 you are looking for. InstanceStatus is the hypervisor's view of the VM; SystemStatus is the guest OS answering. Only the second one tells you Linux is up.

08Non-admin

Run the identical call as the non-admin

Same region, same image, same type. The only thing that changed is the credential on the request.

aws ec2 run-instances --profile dev \
  --image-id $AMI --instance-type t3.micro --count 1
An error occurred (UnauthorizedOperation) when calling the RunInstances operation: User: arn:aws:iam::123456789012:user/dev-bob is not authorized to perform: ec2:RunInstances on resource: arn:aws:ec2:us-east-1:123456789012:instance/* because no identity-based policy allows the ec2:RunInstances action

Read it as three facts: who (dev-bob), what (ec2:RunInstances on instance/*), and why (no identity-based policy allows — an implicit deny, not an explicit one). If a policy had said Deny, the reason would read “with an explicit deny”. That distinction tells you whether to add an allow or hunt for the deny.

04

What “us-east-1 + default VPC” actually buys you

“Default VPC” is not one object. It is a region, a network, six subnets, a route table, a gateway and a firewall — created together, and scoped to different things.

This is why --subnet-id is optional but --key-name is not. The default VPC supplies a subnet, a route and a public IP without being asked. It cannot supply a key pair, because keys are regional objects you create yourself — and it will not let SSH in, because its only inbound rule is self-referencing.

05

Why the non-admin failed

IAM answers one question per call: is there an allow? It checks policies in a fixed order, and “no policy” is a valid, complete answer — it means deny.

#CheckIf it failsdev-bob
1An explicit deny in any applicable policy — SCP, identity, boundary, resource or sessiondeny — nothing overrides itno denial exists
2An SCP above the account allows the action (Organizations only)denynot in an org
3A permission boundary, if one is set, also allows itdenyno boundary set
4An identity policy or resource policy allows itimplicit denystops here
5A session policy, if one is set, allows itdenyno session policy
6Nothing failedallow—

Three answers, not two. Allow means a statement matched. Implicit deny means nothing matched — the default, and what bob hits. Explicit deny means a Deny statement matched, and it outranks every allow in the account. The error message distinguishes the last two, which is the fastest way to know whether to add a policy or go hunting for one that is blocking you.

06

Giving the non-admin exactly one launch

Not AdministratorAccess, and not AmazonEC2FullAccess either — that allows any instance type in any region, and lets the holder terminate everything in the account.

01Policy

The document

Save as launch.json. Replace the account id, and keep the resource ids from step 02.

02Attach

Attach it through a group, not a user

Groups make the intent legible: ec2-launchers is a role in the organisation, not a permission grafted onto one person.

aws iam create-policy --policy-name ec2-launch-default-vpc \
  --policy-document file://launch.json

aws iam create-group --group-name ec2-launchers
aws iam attach-group-policy --group-name ec2-launchers \
  --policy-arn arn:aws:iam::123456789012:policy/ec2-launch-default-vpc
aws iam add-user-to-group --group-name ec2-launchers --user-name dev-bob
03Verify

Test the decision before you test the launch

The policy simulator answers without creating anything, which is much cheaper than a failed RunInstances in a loop.

aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::123456789012:user/dev-bob \
  --action-names ec2:RunInstances ec2:TerminateInstances \
  --resource-arns arn:aws:ec2:us-east-1:123456789012:instance/* \
  --query 'EvaluationResults[].[EvalActionName,EvalDecision]' --output text
ec2:RunInstances allowed ec2:TerminateInstances implicitDeny

That pair of answers is the whole point: bob can create, and cannot destroy. Add ec2:TerminateInstances only if the workflow genuinely needs it.

04Detail

Why one action name needs four resource ARNs

This is the part that surprises everyone. RunInstances is a single API call that creates three resources and references four more, and IAM checks every one of them in the same evaluation.

  • Created by the call — the instance, its root EBS volume, and an ENI. All three need Allow on their own ARN.
  • Referenced by the call — the AMI, the subnet, the security group and the key pair. Each also needs Allow, or the call is denied for that resource.
  • Not resource-scoped — Describe* actions do not support resource ARNs, so they must be "Resource": "*". This is why a policy that looks over-broad in one statement is actually correct.
  • Encrypted AMIs add kms:CreateGrant, kms:GenerateDataKeyWithoutPlaintext and kms:Decrypt on the key — the most common “but I allowed RunInstances” surprise.

Leave out any one of these and the error names exactly the missing resource type — ...on resource: arn:aws:ec2:us-east-1:123456789012:volume/* — which tells you which block to extend.
